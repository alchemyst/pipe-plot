# Refinement issue #32: metadata consolidation evaluation

## Decision

**Defer a production migration.** A single versioned SQLite metadata payload is the simplest candidate for a future atomic raw-row/metadata transaction, but the current sparse capture target does not justify a migration now. The split store has a measurable per-row rewrite cost; for one ten-column producer delivering a row every five seconds over a week (120,960 rows), the measured append is 0.733 ms per row in a short local run, far below the five-second interval. This does not measure ten independent producers. A process crash between SQLite and JSON commits currently has count/bounds repair for known streams. Consolidation would remove that gap and compensating remap rollback, but would not remove full-graph encoding or the cost of growing event-guide history. It introduces a consequential legacy import and downgrade boundary. No production storage code changed in this issue.

The event-history case deserves renewed measurement if guides become numerous: 1,000 event guides made the metadata file about 126 KB and raised later one-stream append time to 2.60 ms per row. This is still small against five seconds, but the guide list is unbounded and a single payload still rewrites it. The observed timing is a one-run local workload, not a week-long resource or SSD-write measurement.

## Current boundaries and invariants

`PipePlotStore` serializes metadata under its recursive lock; `SampleStore` has its own lock and WAL connection (`journal_mode=WAL`, `synchronous=NORMAL`). The JSON sidecar stores sessions, charts, streams and their summaries, guides, timeline, deleted/open state, target chart, next public number, chart recency and open-session restoration IDs. It has no explicit format version. These mutations all call `persist`/`persistSnapshot`: session/chart create, rename, reorder, hide/delete/restore and open state; target and termination-open set; sampler/event registration and finish; numeric and text-event append; rejected-input count; stream movement, reassociation, layout/style and derived settings; guides, time zone/reference, timeline, selection and forecasts; and undo/redo replay. Registration suppresses intermediate writes and commits one snapshot after validation. Normal user edits restore `committedState` on a failed JSON write.

Raw samples, allocated sequences, stream counts/bounds and fit revisions live in SQLite. `SampleStore.append(values:...)` commits all columns in one `BEGIN IMMEDIATE` transaction before `PipePlotStore.append` updates its memory summary and rewrites JSON. That method advances `committedState` before the JSON write: if JSON fails, it throws without a row acknowledgement, yet committed raw rows and the active producer remain in memory. On startup, JSON is decoded, saved live/quiet streams become disconnected, windows close, and every **known** stream's count and time bounds are recomputed from SQLite. Missing or malformed JSON is not repaired; malformed JSON throws, while missing JSON with pre-existing raw rows currently yields an empty session catalog. Direct users of the public `samples` property can also write raw rows without adding a stream record.

After `store.append` returns, `IngestionService` obtains a snapshot and evaluates crossing alerts, then sends `accepted`. A commit can therefore survive with no acknowledgement if JSON, later processing, or socket send fails; an acknowledgement implies the store method completed but does not promise survival of power loss under WAL `NORMAL`. There is no durable exactly-once retry protocol. Text events live only in JSON and are acknowledged after `appendEvent` returns. A failed event write rolls back the guide. The service finalizes both numeric and event sockets through `PipePlotStore.finishAttachment`, which marks `committedState` before persisting and keeps the in-memory finished state on JSON failure. The separate public `finishEventConnection` method does not mark `committedState` and can restore an active in-memory attachment on failed persistence, but the service does not call it.

Undo/redo stacks, owners, active attachments, continuation and epoch are process-local. Each session undo stack is capped at 200 actions; ordinary arrivals do not create undo steps or clear redo. Restart does not restore those stacks or producers. Reassociation moves whole segment IDs in a SQLite transaction, changes memory and JSON, and on a JSON failure attempts a compensating reverse SQLite transfer. Undo/redo reassociation uses the same pattern. A process exit between transfer and JSON/compensation can leave raw segment ownership different from the old JSON layout; startup repairs counts/bounds but does not reverse that mapping. A replacement must preserve stream/segment IDs, arrivals during capture, live undo semantics, and all-or-nothing row groups without copying raw history into undo.

## Isolated measurements

Run `scripts/research/evaluate-issue32.sh` from this checkout. It compiles the core with `swiftc -O`, creates only temporary stores, runs each workload once, and removes them. This run used macOS 27.2, arm64, Swift 6.4.2 and Python 3.11.6. The `core` comparator calls `SampleStore.append` for the same rows without domain bookkeeping or JSON. It is not a breakdown of encoding versus filesystem cost.

| Actual store workload | JSON before → after | `PipePlotStore` append | `SampleStore` only |
| --- | ---: | ---: | ---: |
| 1 session/chart/stream, 1,000 rows | 824 → 878 B | 0.322 s | 0.066 s |
| 21 sessions/charts, 1 active stream, 1,000 rows | 11,829 → 11,883 B | 0.585 s | 0.068 s |
| 1 session/chart/stream, 5,000 rows | 824 → 878 B | 1.559 s | 0.381 s |
| 21 sessions/charts, 1 active stream, 5,000 rows | 11,829 → 11,883 B | 2.897 s | 0.337 s |
| 1 session/chart, one 10-column producer, 1,000 rows | 2,211 → 2,751 B | 0.733 s | 0.489 s |

All counts matched the input per stream. The extra-session fixture holds active column count at one, isolating metadata-size growth from SQL-column growth. Numeric history itself barely changes JSON size; stream summaries account for its small increase. With one stream plus 100 or 1,000 event guides, JSON grew from 824 B to 13,103 or 125,603 B. Adding those guides took 0.036 or 1.353 s respectively; the **next** 1,000 numeric appends took 0.552 or 2.602 s (final JSON 13,157 or 125,657 B). Guide cardinality is a different workload from numeric history length.

Two child processes exited with `_exit(0)` and reopened separate temporary fixtures. A direct `samples.append` after the first public row models the exact **post-SQLite/pre-JSON state**, but is not a crash injected inside `PipePlotStore.append`: JSON count 1, SQLite count 2, reopened in-memory count 2, stream disconnected and session closed. A second child returned from public `PipePlotStore.append`, recorded a local acknowledgement marker in place of a socket send, then exited: JSON, SQLite and reopened counts were 2. Neither fixture simulates a physical power interruption or proves an actual network acknowledgement.

The Python model in the same script holds raw sample inserts, indexed schema, stream-count update, one transaction per row, WAL and `NORMAL` constant. It compares an atomic sidecar rewrite after commit, an `UPDATE` of one versioned SQLite payload row, and an `UPDATE` of a small normalized session row. For 5,000 rows at 878 / 11,883 / 125,657 payload bytes, elapsed times were **1.463 / 1.282 / 1.174 s** (sidecar), **0.310 / 0.284 / 0.578 s** (payload), and **0.335 / 0.271 / 0.275 s** (normalized subset). These are isolated storage-boundary models, not production speedup estimates: the payload is a reused opaque `x`-byte buffer with an eight-byte counter, the normalized path updates only a tiny subset, and Python's statement cache and simplified SQL omit the real sequence allocator, JSON encoding and domain graph. The larger payload already costs more than the tiny normalized update; a full payload would still encode the growing guide list.

## Alternatives and conditional design

| Option | Benefit | Cost and limit |
| --- | --- | --- |
| Keep split JSON + SQLite | No migration; JSON is inspectable; sparse capture is comfortably below its interval; existing known-stream count repair works | Two commit boundaries, per-row full rewrite, remap compensation and possible inaccessible raw rows if metadata is missing |
| One versioned SQLite payload | Raw row, summary and metadata can commit together; metadata-only edits can use one transaction; little schema mapping | Still encodes and writes the entire graph; guide growth remains; requires safe migration and explicit downgrade handling |
| Normalized metadata tables | Can update small affected rows and append guides without rewriting the graph | Largest schema/API and migration change; many relationships, ordering, optional fields and edit rules; the tiny model does not price this work |

If later evidence warrants consolidation, prefer the versioned payload first, then decide separately whether event guides need their own append-only table. Keep raw sample tables and query limits unchanged. Treat legacy `PersistedState` as format 0. Add a singleton `app_metadata` table with `id INTEGER PRIMARY KEY CHECK(id=1)`, `format_version INTEGER NOT NULL`, `generation INTEGER NOT NULL`, `payload BLOB NOT NULL` and `legacy_fingerprint TEXT`; reject unknown versions. Do not silently use `PRAGMA user_version` as the format authority while existing databases have no managed schema version. Decode legacy optional fields as today and retain all stable IDs. Future `PipePlotStore.append` must stage memory, raw row inserts, stream summary and payload within one SQLite transaction under existing lock order, commit before returning, restore memory on failed commit, and never acknowledge an unverified commit. Reassociation must include segment transfer and metadata in that same transaction; live undo stacks may remain process-only.

An import should run only with capture stopped and one app instance. First validate and decode legacy JSON, inspect raw rows and known stream references, and create a **consistent** SQLite backup through SQLite's backup API (or a checkpoint-aware equivalent), plus a verified JSON backup. Never copy only the main `.sqlite` file while WAL is active. Before SQL cutover, atomically put a fail-closed sentinel at the legacy JSON path so an older binary cannot silently write stale metadata; preserve the original in the backup. The new loader must recognize the sentinel and resume from the backup. In one `BEGIN IMMEDIATE` transaction reconcile known-stream summaries, insert the versioned payload and import marker, and commit. After commit, the SQL payload is authoritative on every startup; stale or modified sidecar JSON must never override it or trigger a duplicate import. A crash before commit resumes from backup; a crash after commit opens the SQL payload. A read-only database, insufficient space or failed backup/import must fail closed without creating a blank catalog or acknowledging new rows. Retain backups until a separate verified reopening and explicit retention policy.

An older binary does not understand the SQL payload. The sentinel makes it fail at startup, but cannot stop an older process that was already running; that is why migration requires exclusive operation. Automatic downgrade is unsafe after new edits or samples. A manual rollback must either export a compatible legacy JSON snapshot from the SQL payload while keeping the current raw SQLite data, or restore the consistent database-plus-JSON backup with an explicit warning that later capture would be lost. Do not restore only old JSON over newer raw data. Under WAL `NORMAL`, a process crash preserves transaction consistency but a power loss may lose recently acknowledged commits; if power-loss durability becomes a requirement, measure `synchronous=FULL` before changing the acknowledgement promise.

## Required gates if migration is reopened

1. Legacy JSON plus SQLite: intact, missing-with-raw-rows, malformed, older optional fields and unknown version; keep acknowledged rows and IDs visible, and fail closed when reconstruction is impossible.
2. Import/restart: repeated startup; exit before sentinel, after sentinel but before SQL commit, and after commit; stale sidecar; concurrent/older binary rejection; verify no duplicate metadata or orphaned sample groups.
3. Failure: read-only path, low-disk/`SQLITE_FULL` during backup/insert/commit, backup corruption, failed JSON sentinel replacement and failed metadata-only edit; verify transaction rollback, clean retry and no false ACK.
4. Runtime: multi-column row commit and ACK, post-commit/pre-socket-send uncertainty, live event append and finish, edit/undo/redo retention, reassociation and compensating-failure removal, WAL reader isolation and bounded sample queries.

Current temporary-store tests cover failed JSON edit/replay, malformed JSON, SQLite full row rejection, committed raw rows after JSON failure, registration rollback and remap compensation. They do **not** cover crash during real method execution, power-loss durability, a migrated database, old-binary concurrency, read-only/low-disk import, or long event histories. A bounded follow-up would first add missing-metadata/orphan detection and explicit lifecycle-failure coverage without changing format; only then prototype import and a single-payload transaction behind an opt-in fixture. Normalized metadata belongs to a separate decision after event-history measurements. No milestone tickets are created here.
