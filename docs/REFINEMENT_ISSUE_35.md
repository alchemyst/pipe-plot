# Refinement issue #35: Swift Charts renderer evaluation

## Decision

**Retain the production Canvas renderer.** The isolated Swift Charts prototypes can draw a useful subset of PipePlot's two-row workload with segmented lines, dots, value/time guides, a selection, a forecast estimate, relative axis labels, and the existing native gesture overlay. The collection-based `LinePlot`/`PointPlot` variant is materially faster than one `LineMark`/`PointMark` per observation, but with the same bounded full-week data its hosted view updates still took 0.778–0.796 seconds for three updates, compared with 0.047 seconds for Canvas. The prototypes also leave several production annotations and interactions unimplemented. The evidence does not justify a renderer migration or a loss of existing menu, visibility, gesture, or accessibility behavior.

This is a **conditional defer**, not a claim that Swift Charts cannot be made suitable. The recommended next step is a small PipePlot-owned, Charts-shaped description of what to draw, consumed first by the existing Canvas renderer; it can make a later Charts adapter easier to compare without committing to a migration. Reopen adoption only if a complete adapter demonstrates visual and interaction parity on the same bounded workload, measured native behavior, and a maintainability benefit worth its measured resource cost. Keep the existing bounded display query and shared accessibility formatting; this prototype did not establish a worthwhile immediate production simplification.

## Prototype and comparison boundary

The prototype lives entirely in `Tests/PipePlotAppTests/SwiftChartsPrototypeTests.swift`; no production renderer, app window, store, or installed copy changed. `scripts/research/evaluate-issue35.sh` creates a temporary SQLite history and a temporary opt-in marker, runs the hosted test in Release configuration with testability enabled, then removes its fixture. The marker is deliberately separate from the acceptance fixture and the user's app database/socket. The existing `PIPEPLOT_TEST_HOST=1` scheme entry runs only the XCTest host, without normal app bootstrap or IPC.

Both paths receive the same `SessionSnapshot`, per-stream `[StoredSample]` display arrays, time domain, now, selection, synthetic forecast drawing, unit and reference-guide configuration. The two aligned rows each contain five streams. Row 0 uses mV-scale values; row 1 uses kPa-scale values. Each stream has a reconnect discontinuity and the first stream in each row has dots. A chart-level value guide and session time guide drive relative Y/time labels. The selection is fixed. The forecast uses a two-point linear fit made from the last displayed observations and is presented only as an **estimate**; it is not a raw observation or a test of PipePlot's forecast fitting policy. Each renderer gets only the forecast owned by that row.

The first prototype uses one `LineMark`/`PointMark` per observation. The second uses collection-based `LinePlot`/`PointPlot` over lean value/time/unique-series/style records derived from the same bounded `[StoredSample]` arrays. Each vector record's series key combines stream identity and reconnect segment; it does not rely on color to separate lines. A handful of `RuleMark`/`RectangleMark` overlays and the axes/scales remain the same. This tests Apple's [vectorized plotting API](https://developer.apple.com/videos/play/wwdc2024/10155/) rather than treating per-observation marks as all of Swift Charts. Both variants reuse `PlotInteractionOverlay`, supplying `ChartProxy.plotFrame` resolved in `GeometryReader` and `position(forX/Y:)` / `value(atX/Y:as:)` conversions. Both reuse `PlotAccessibility` to provide the same summary and chart descriptor as Canvas; the prototype's chart content is one labeled image element. That accessibility bridge and native overlay are part of the implementation cost, not free Swift Charts behavior. Apple's [ChartProxy plot frame documentation](https://developer.apple.com/documentation/charts/chartproxy/plotframe) describes the anchor as the plot area excluding axes.

The sample-store display query retains first, last, minimum and maximum observations per one of 800 time buckets. The test verifies that every seeded stream yields nonempty data and no stream exceeds 3,200 displayed observations. The test never materializes the 1,209,600-row history as UI arrays.

| Case | Raw fixture | Base display arrays sent to each renderer |
| --- | ---: | ---: |
| Sparse | 10 streams × 180 one-minute observations | 1,800 observations |
| Live 15 minutes | 10 streams × 120,960 nominal five-second observations over a week, with one three-minute reconnect pause | 1,810 observations |
| Full week | Same SQLite history | 31,870 observations |

SQLite seeding and display queries are outside renderer timings. Each of the three update submissions replaces `NSHostingView.rootView` with a five-second later clock and selection plus **one** additional bounded observation per stream relative to the base arrays. The update arrays contain base + 10 observations each; they reset from the base on every iteration rather than accumulate to base + 20 and base + 30. This is an accelerated UI-update fixture; the user's sparse one-minute source cadence would issue fewer updates. No acquisition, IPC, database write, background query, animation completion or physical display scanout is included.

## Observations

The run was on 2026-11-03, Mac14,9, 16 GiB RAM, macOS 27.2 (26B123), arm64, Xcode 27.2 (27B52), Apple Swift 6.4.2. The hosted app/test target used Release `-O` and `ENABLE_TESTABILITY=YES`; the test ran in its own process with `PIPEPLOT_TEST_HOST=1`. The generated history held 1,209,600 rows in a temporary database. The order within each case was Canvas, per-observation Charts, vectorized Charts, vectorized Charts, per-observation Charts, Canvas to expose first-use and cache effects. These are one local run with two trials per path, not statistical confidence intervals.

| Case | Canvas three updates (s) | Per-observation Charts (s) | Vectorized Charts (s) |
| --- | ---: | ---: | ---: |
| Sparse | 0.0132 / 0.0175 | 0.1010 / 0.0976 | 0.0617 / 0.0593 |
| Live 15 minutes | 0.0140 / 0.0126 | 0.0967 / 0.1028 | 0.0567 / 0.0553 |
| Full week | 0.0475 / 0.0467 | 1.4942 / 1.4983 | 0.7779 / 0.7957 |

Mount includes window and host construction, view mounting, layout and display submission, so its first value is strongly affected by framework and cache warmup. In the full-week case, mounts were 0.058/0.036 seconds for Canvas, 0.526/0.527 seconds for per-observation Charts, and 0.287/0.278 seconds for vectorized Charts. The update column is the more useful paired comparison because all paths actually receive new bounded snapshots and time/selection values. It still measures synchronous host/layout/display submission rather than frame presentation. Querying the last 15 minutes took 0.170 seconds and the full week 3.055 seconds in this run, separately from any renderer; these query figures are warm/cold and storage-cache sensitive.

`mach_task_basic_info.resident_size` was sampled before mount, after three updates and after window close. Charts is linked into the same hosted process even while Canvas is active. In this run's full-week sequence, the first Canvas trial went **217.6 → 222.7 MB**, the first per-observation Charts trial **222.7 → 435.1 MB**, the first vectorized Charts trial **342.1 → 568.3 MB**, the second vectorized trial **568.4 → 685.3 MB**, and the final Canvas trial **789.8 → 790.8 MB**. RSS sometimes fell after a close and sometimes remained high; the whole process peaked near 791.9 MB. There was no settled post-close or idle baseline: back-to-back synchronous XCTest updates may defer cleanup. These values cannot distinguish caching, deferred release, or leaks, and do **not** isolate each renderer's standalone steady-state memory, chart framework load, or a production app footprint. They do not establish that vectorized Charts uses more steady-state memory than per-observation Charts. A future decision would require separate-process, repeated measurements with identical menus/windows and cache conditions.

Before constraining the Y-axis label lane, the two Swift Charts plot frames began at x=42 and x=66 points because the rows' relative values and units had different label widths. A 56-point label lane made both x=60. Calibrating the lane to 52 points plus a chart-plot top/bottom padding of 4/1 points made **both Swift Charts variants' actual plot frames x=56, y=4, width=944, height=288**, identical to Canvas in the 1,000-point hosted window. ChartProxy mapped lower/mid/upper X values to Canvas's 56/528/1000 point positions, and the lower Y value to the shared 292-point bottom; native hover at 10 points inside resolved to the corresponding domain time within half a pixel's time span. The calibration is explicit bridging code and needs review at narrower windows, larger fonts and longer units/values, where a fixed lane may clip labels.

Direct native `PlotInteractionView` shift-drag events reached the pan callback on all three paths. Dispatch for two rows remained sub-millisecond in sparse/live cases after initial warmup, with variable full-week timings under allocation pressure. This measures direct event/callback work in XCTest; it is not a physical trackpad response or end-to-end pan frame. A production `SnapshotMenuItem.menu` remained tracked through a hosted root-view update for each path in the sparse case, and all hosted windows passed `orderOut`/reveal checks. That demonstrates compatibility with the snapshot menu object and NSWindow visibility in the harness; it does not verify PipePlot's full WindowGroup command routing, actual pointer movement, menu selection, occlusion, or FocusedValue behavior after a migration.

## Complexity and parity

The shared Swift Charts prototype view is about 225 lines for both mark strategies, axes, scales, accessibility and ChartProxy/gesture integration, plus reconnect/stream identity encoding, a research stack, an interactive preview view and a larger fixture/measurement harness. The existing Canvas drawing file is 498 lines; gesture overlay and accessibility support are separate files of 415 and 217 lines and remain required by both prototype variants. A simple line-count comparison would be misleading: the prototype omits guide badges and collision placement, extrema/latest labels, forecast training brackets, the Canvas-specific linked-boundary button and mode cues, hover/now labels, derived overlays, hidden and marks-off combinations, error/loading states, and dynamic chart actions. The shared native overlay's selection handles are present in the prototype and were visible in preview. A production Charts implementation would need to preserve or rebuild the remaining behaviors. Chart's automatic accessibility alone was not accepted as parity; the prototype explicitly reuses the current adapter, while runtime VoiceOver and `AXChartDescriptor` export remain unverified.

### Maintenance benefit to prove

| Responsibility | What the prototype shows |
| --- | --- |
| Series drawing, clipping, scale mapping, basic axes and grid | Swift Charts supplies marks, plot clipping, scale domains, tick/grid placement and plot coordinates. That can remove Canvas's manual line paths, dot loops, grid paths, tick positions and basic x/y mapping. The collection API also handles many displayed points with fewer mark declarations. |
| PipePlot semantics and native interaction | The app still owns bounded SQLite queries, stream/reconnect identity, chart-level units and reference formatting, now/selection/guide state, forecast meaning, custom AppKit gestures, menu behavior and the `AXChartDescriptor`/summary adapter. `ChartProxy` conversions and a calibrated axis-label/plot inset are new bridge code. |
| Full visual parity | Guide badges, latest/extrema labels with collision placement, training brackets, the linked-boundary button and mode cues beyond the shared overlay handles, hover readouts, derived traces and loading/error/marks-off states need implementation and native review. Their placement may use chart annotations, overlays or custom Canvas drawing, and could erase much of the apparent code reduction. |

The prototype demonstrates a smaller **basic plot implementation**, not a smaller feature-complete renderer or lower lifetime maintenance cost. The current update-cost result is a material tradeoff, especially for full-history navigation, but performance alone does not settle the choice. If a complete Charts version demonstrably reduces custom code and maintenance while preserving native menus, window behavior, accessibility and interaction, the user may reasonably accept a measured performance cost at their actual workload. That case has not yet been established, so the production migration remains deferred.

### Proposed follow-up: a small render contract

Extract a bounded render description from the current `PlotCanvas` inputs: visible streams split into segment series with line/dot styles, axis domains and formatted ticks, value/time rules, selection bounds and forecast estimates. Keep raw-observation identity and estimate provenance explicit. Canvas should consume that description with its existing geometry and drawing behavior, while the native gesture overlay, menus and accessibility adapter continue to use their current session/model state. A compact coordinate contract should describe plot bounds and time/value conversion so a later renderer can be tested against the same ruler, guides and gestures.

The work should be incremental: first capture current Canvas output and coordinate invariants with bounded fixtures; then extract one drawing responsibility at a time while keeping the native result unchanged; finally build an optional Charts adapter over the same description and rerun these sparse/live/week and native checks. Existing snapshot DTOs, `PlotInteractionOverlay` and `PlotAccessibility` already provide a starting point. The extraction itself must demonstrate less duplication or clearer ownership: copying the full Swift Charts modifier DSL/API into PipePlot would add another framework to maintain. This is a proposed follow-up, not a production rewrite or a new GitHub ticket in issue #35.

An initial vectorized attempt put one `LinePlot` inside each stream/segment `ForEach`. Native preview showed false diagonal connections between streams: Chart merged those plots into a common series. Its timings are excluded from the final comparison. The corrected collection has an explicit unique series projection; native preview showed distinct bands and real reconnect breaks. The first fixture also produced identical cyan colors because its deterministic UUIDs shared the bytes used by Canvas's palette hash; explicit `colorHex` values were added for visual inspection. Color was never used to separate line geometry.

The opt-in preview kept two actual hosted `NSWindow` instances alive under `PIPEPLOT_TEST_HOST=1`, using the same bounded SQLite-derived arrays. Desktop UI inspection saw distinct colored stream bands with no cross-stream diagonals in the corrected vectorized variant, the same positions and shapes as Canvas in the live view, and a clear three-minute reconnect break in both Charts rows when the shared Plot navigation menu switched to a bounded midpoint query. The initial selection band crossed both rows, a dashed forecast estimate was visible in Charts, and the same selection and forecast DTOs were present in Canvas. Relative axes/time, guide and Now positions aligned. The native accessibility tree exposed chart images and values on both paths, and its values updated when the menu changed the range. These are runtime observations from the isolated hosted windows, not full production `WindowGroup` acceptance.

The preview's Show-other-window button did not reliably switch windows after the range update in desktop UI automation, even after changing the hold to yield the MainActor. Earlier initial switching worked. This is unresolved in the preview harness; it is neither evidence of a production loss nor evidence of complete window/menu parity. The vectorized prototype still lacks Canvas's guide badges, latest/extrema labels and other behaviors listed above. Physical pan/zoom, keyboard command dispatch, all app menus, long-run occlusion, low-memory behavior, gesture frame pacing, spoken VoiceOver/chart audio, and minimum-window layout remain unverified. The present Canvas has existing native evidence in `docs/REFINEMENT_ISSUE_34.md`, but its broader lifecycle acceptance remains separate.

## Reproduction and validation

Run `zsh scripts/research/evaluate-issue35.sh` from any directory. It prints one `CHARTS_RESEARCH` record per trial, including bounded count, mount and three-update times, current RSS and process peak RSS; it also prints ChartProxy frames, native pan dispatch, menu tracking and query times. `zsh scripts/research/evaluate-issue35.sh preview` opens the two interactive hosted windows with a shared live/reconnect range and holds until `/tmp/pipeplot-issue35-preview.release` is created or 20 minutes elapse. Use preview only while deliberately inspecting the test host; after it exits, do not query the app through computer use without another explicit test launch. The script removes its temporary SQLite fixture and opt-in markers on exit. Do not use the resulting timings as a regression threshold on other machines. Ordinary `just test` skips both opt-in tests.

The final corrected opt-in Release comparison passed one test, zero failures. The interactive hosted preview also completed its selected test after release. The first Release attempt without `ENABLE_TESTABILITY=YES` could not import the app module in the test target; the corrected script includes that setting. Full package/hosted tests and strict build results are recorded below after the final run.

- `PIPEPLOT_XCODE_DERIVED_DATA=/tmp/pipeplot-issue27-xcode.YP4Sbt just test`: 100 package tests passed (84 Core, 12 Transport, 4 CLI); hosted Xcode suite executed 79 tests, with 75 passed, four opt-in skips and zero failures. The two new research tests are both skipped by default.
- `PIPEPLOT_XCODE_DERIVED_DATA=/tmp/pipeplot-issue27-xcode.YP4Sbt just strict-build`: passed Swift 6 warnings-as-errors package tests and hosted app/test build-for-testing. Xcode reported no Swift compiler warnings; App Intents metadata extraction was skipped because the app does not depend on that framework.
- `just format-check`, `git diff --check` (including intent-to-add untracked files) and `zsh -n scripts/research/evaluate-issue35.sh`: passed.
